==============================================================================
A. THE FAILURE THIS PHASE EXISTS FOR, AS THE USER EXPERIENCES IT
==============================================================================

`saveVersion` and `computeAndSaveLinks` fire un-awaited from routes/notes.js on
every note save. Before 6.3 their failures reached console.error and nothing
else. PRIMER §9.1 has predicted this mode since the plan was drafted, and 7.1
had to REJECT it from docs/FAILURE-MODES.md for having no frequency — there was
no instrument that could count it.

Reproduced by replacing the write target with a MongoDB VIEW, which every write
refuses. NO PRODUCT CODE WAS MODIFIED TO PRODUCE THE FAILURE: it is a real
driver error from a real broken database object, not an injected fault, and
there is no fault-injection flag anywhere in the shipped code.

  db.notelinks.drop()
  db.createCollection("notelinks", { viewOn: "notes", pipeline: [...] })

What the user then sees on a save:

  PUT /api/notes/:id                200 OK
  the note itself                   saved, normalized, keywords extracted
  the related-notes panel           EMPTY — and stays empty
  the only signal, pre-6.3          one line on the server's stdout:
      Background linking error: Namespace dsb_63_verify.notelinks is a view,
      not a collection

  An empty panel and a note with genuinely no related notes are INDISTINGUISHABLE
  to the user and to every metric in this repository. That is what "invisible by
  construction" meant.

==============================================================================
C. THE SECOND JOB, AND IT HAD A DEFECT ONE LAYER DEEPER
==============================================================================

CLAUDE.md says both background jobs' failures "only reach console.error". That
is true of computeAndSaveLinks. It is NOT true of saveVersion, which has its own
try/catch, logs, and returns null — so its rejection never reaches the call site
at all and the call-site `.catch` had never once fired.

A span wrapped only around the call would therefore have been GREEN on every
failure: §22.6's shape, a check that runs and cannot fail, met for the third
phase running (§37.3, §38.6). One line inside that existing catch closes it —
version.service.js calls failActiveSpan(err) before it logs and returns null.

Verified by breaking the versions collection the same way:

  traceID                   27a6f99e76c9ca550af910b76afa562d
  span                      background-version       6.67 ms   [UNCONTROLLED]
  otel.status_code          ERROR
  otel.status_description   Namespace dsb_63_verify.noteversions is a view, not
                            a collection
  exception.message         (same)
  dsb.job.origin_trace_id   df6fc661922851b3b594ddf1e557cd85

  WHICH CATCH FIRED IS VISIBLE IN THE LOG AND IT IS THE INTERNAL ONE:

    Version save failed (non-critical): ...     <- version.service.js's own
    Version save skipped: ...                   <- routes/notes.js's — NEVER SEEN

  The call-site label does not appear in any run. The span is red anyway. That
  is the whole point of the one-line change.

==============================================================================
D. WHY A LINKED SPAN AND NOT A CHILD SPAN — MEASURED, NOT PREFERRED
==============================================================================

A child span would have been one line shorter. It is refused because a child
that OUTLIVES ITS PARENT is exactly what un-awaited means, and Jaeger derives a
trace's duration from max(end) - min(start) across ALL of its spans. Attaching
the jobs as children therefore inflates the note-save trace's listed duration
above the time the user actually waited.

Computed over every save in this session where the origin trace and its job
spans are both present:

  saves examined                       25
  inflated                             25 of 25
  inflation  min                       36%
             median                    135%
             max                       266%

  the PUT saves specifically (both jobs each):

    root 30.91 ms   as a child: 42.19 ms   +36%
    root 26.33 ms   as a child: 38.34 ms   +46%
    root 17.59 ms   as a child: 25.93 ms   +47%
    root  9.39 ms   as a child: 16.02 ms   +71%
    root  8.51 ms   as a child: 13.69 ms   +61%
    root  5.67 ms   as a child:  9.84 ms   +74%
    root  5.42 ms   as a child:  8.52 ms   +57%

⚠️  READ THE SIGN, NOT THE SIZE. The DIRECTION is arithmetic and guaranteed: a
    span that ends after its parent can only increase max(end) - min(start), so
    the inflation is never negative and 25 of 25 is not a sample result. The
    MAGNITUDE is a ratio of two uncontrolled durations on one laptop and is NOT
    a performance figure; a different machine, a warm cache or a larger corpus
    moves every number in the table. What the table establishes is that the
    distortion is LARGE ENOUGH TO MATTER, not how large it is.

    Both the request trace and the job trace are honest under the shipped
    design: the note-save trace lists what the user waited for, and the job
    carries its own duration in its own trace.

  ALSO REFUSED, and for a different reason: SpanKind PRODUCER/CONSUMER. Those
  describe a message crossing a broker. Nothing is queued here — PRIMER §11's
  rejection of Redis + BullMQ is why — so the kind stays INTERNAL.

==============================================================================
E. TWO THINGS THAT WILL LOOK LIKE BUGS TO WHOEVER HITS THEM
==============================================================================

E.1  `exception.type` IS A NUMBER, NOT THE ERROR CLASS.

     The span above reports exception.type = 166 where a reader expects
     MongoBulkWriteError. This is OpenTelemetry's own precedence rule, read from
     the installed source rather than assumed —
     @opentelemetry/sdk-trace/build/src/Span.js:304 :

       if (exception.code)      attributes[EXCEPTION_TYPE] = exception.code.toString();
       else if (exception.name) attributes[EXCEPTION_TYPE] = exception.name;

     MongoDB driver errors carry a numeric `code`, so `code` wins and the class
     name survives only inside exception.stacktrace. 166 is MongoDB's code for
     "namespace is a view".

     NOT WORKED AROUND. Stripping `code` off the error before recording it would
     be discarding the more precise identifier to make the less precise one
     display — and any error class carrying a `code` behaves this way, so the
     fix belongs upstream or nowhere.

E.2  THE `error` TAG IS VISIBLE IN THE UI AND NOT FINDABLE BY TAG SEARCH.

     Measured against the same trace, same lookback, same limit:

       tags={"error":"true"}                      0 traces
       tags={"error":true}                        0 traces
       tags={"otel.status_code":"ERROR"}          0 traces
       tags={"dsb.note.id":"6a8b31656ca1424..."}  3 traces
       tags={"dsb.job.origin_trace_id":"..."}     2 traces   <- both jobs of one save

     `error` and `otel.status_code` are DERIVED by Jaeger's v1 API from the OTLP
     span status; they are rendered as tags but are not indexed as tags. Real
     attributes are. This is §38.2's finding in a second costume — there, the v1
     tag model flattened an array attribute so a UI filter silently matched
     nothing; here it synthesises tags a filter cannot match at all.

     THIS IS EXACTLY WHY THE CAUSAL EDGE IS RECORDED TWICE. The OTel Link is the
     correct record and is what a conformant backend reads; Jaeger v1 renders it
     as a FOLLOWS_FROM reference in the span DETAIL panel, not in the waterfall
     and not in search. dsb.job.origin_trace_id is a plain string attribute, so
     it IS indexed — and the last row above is the payoff: one query returns
     every background job descended from one save.
