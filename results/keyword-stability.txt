══ D. WHAT RECOMPUTING AT READ TIME WOULD COST ══════════════════════════
   Prices ONE design option: dropping stored note.keywords and extracting
   on every read instead. extractKeywords rebuilds the whole df table per
   call (utils/keywords.js:71), so extracting N lists is N x O(N*K).

   N =  500   extract all lists   min 2196.7 ms  p50 2202.8 ms  max 2262.4 ms
   N = 2000   extract all lists   min 9399.7 ms  p50 9477.3 ms  max 9524.4 ms

   Against 4.4's measured buildGlobalGraph: 5.1 ms at N=500 and 43.9 ms at
   N=2000 (results/graph-characterization.txt). The comparison is the point —
   read-time extraction is the term 4.4 removed from this function, put back
   one layer up.

══ WHAT THIS DOES NOT ESTABLISH ═══════════════════════════════════════
   - NOT a measurement of a notebook. Stack Exchange cooking questions
     shaped as Notes; §12.2 says the same thing about the same slice.
   - NOT a quality claim. It measures whether a list MOVED, never whether
     the list it moved to is better. No answer key here grades keywords.
   - NOT a latency claim. Section D is CPU in one process, no Mongo, no
     network, no serialisation, and the environment is printed with it.
   - NOT extrapolable across N. Every figure names its own.
   - NOTHING about graphBuilder.service.js:10's third tokenizer, which has
     no corpus and therefore neither of these two defects.
